# Key bootstrap and the gate status: Dinis's one exception

Built by cl-6.infra@PrompTugal.dinis with cl-6.security@PrompTugal.dinis, 26 Nov 2026. Design: PrompTugal__Agent__Security `docs/security/2026-11-26-section-repos-key-bootstrap.md` (6fbdbc8). Policy: `policy/key-bootstrap.json`.

## What it does
- **Key bootstrap** (`.github/workflows/key-bootstrap.yml`): for a section agent's key pull request that cl-6.security has approved (a detached signature in its home over the exact head SHA and diff hash), PrompTugal__IaC checks every rule in the policy (the pull request's base is dev's head and dev's head is the last verified anchor; only team/keys.json in the repository's key format and files pinned whole by sha256 in cl-6.security's signed pins change; the whole file list is read, and 300 or more files are refused), merges that pull request at that SHA, checks the merged tree is the approved tree, sets `SIG_BOOTSTRAP_ANCHOR` to the merge, and deletes it after the first green run on dev or after 24 hours. One repository per run.
- **Gate status** (`.github/workflows/gate-status.yml`): posts `promptugal-iac/gate` on dev and work/* heads of the covered repositories. On dev it compares from the anchor A, on work/* from dev. Success when `.github/**`, `scripts/**`, `team/**` and `.gitattributes` are untouched; when they are touched, only with cl-6.security's signed approval of that SHA; failure when A is unknown or the file list may be cut.
- **dev-gate ruleset** (Org apply, `org/repos.json`): on dev of the covered repositories, no deletion, no force push, and the gate status required, bound to the App, so a same-named status from a pushed workflow does not count. Created only once the status is on dev. Bypass: organisation admins only. An approved key pull request carries the gate status through cl-6.security's gate approval of its head SHA.
- **PrompTugal__IaC itself**: `main-locked` and `dev-safe` rulesets (no deletion, no force push, a pull request required, with no approvals counted: fine while only Dinis merges policy changes).
- **Per repository** (`repository_config`): the job whose pass makes a pages.yml run the anchor, and the key format (Signals: P-256 `git_signing.pem`). Cyber needs both verify and leakscan.
- **Whole-file pins** (`pinnable_files`, `pins`): each repository's new pages.yml, Travel's check-commits.mjs, Signals' leak-scan.mjs and Data's check-commits.mjs, check-signatures.mjs, leak-scan.mjs and test-leak-scan.mjs are pinned by sha256 in cl-6.security's signed `approvals/pins/<repo>.json`, only for the files this policy lists per repository. No further merge by Dinis.

GitHub does not allow file-path push rules on public repositories (rules probe run 45743552530: HTTP 422), so the gate is a required status.

## What Dinis does, once
1. Merge this pull request.
2. Add to the App's PrompTugal installation (agenticcells-site-factory): **Commit statuses: write**, **Variables: write**, **Pull requests: write**, **Workflows: write**, **Actions: read**.
4. Later, once: merge the pins update (the reviewed pages.yml of each repository, Travel's, Signals' and Data's gate files, and the anchor jobs for Cyber, Videos and Travel). Each run mints tokens with only the permission its step needs, for one repository.
3. Turn on the two schedules: uncomment the `schedule` lines in `key-bootstrap.yml` and `gate-status.yml` (15 minutes), or tell cl-6.infra to.

After that, new or rotated section keys need no one but the agent and cl-6.security. A broken approver chain, or a change to the policy, comes back to Dinis.

## Agents' release flow
With dev-gate on, a commit lands on dev only once it carries the App's status. Agents push `work/<agent>` only, never dev (cl-6.decisions, 27 Nov 2026). Each Gate status run posts the status on that head and, when it is success and a strict fast-forward of dev, the App moves dev to it (force false). A failure leaves dev alone and creates the tag `gate/<agent>/<sha12>-fail`. The agent reads the outcome with `git ls-remote origin dev` and `git ls-remote --tags origin 'gate/<agent>/*'`, waiting up to about 20 minutes; it needs no GitHub API. If dev moved under it, it merges `origin/dev` into `work/<agent>` (never a rebase) and pushes again as a plain fast-forward: **no force anywhere**, on any branch (ABP P19: push `work/<agent>`, no force). That works because the gate compares dev...head, which after the merge holds only the agent's own changes, and the App needs only that dev is an ancestor of the head. To drop a commit the gate refused, the agent reverts it (a new commit) rather than rewriting the branch. The merge commits are signed like any other. Only the App's own status counts: one created by `agenticcells-site-factory[bot]` (id 357166223), the newest if there are several; a `promptugal-iac/gate` status from any other account is ignored. The name `work/<agent>` is not tied to who pushed it: the gate judges content and signatures, and each agent's ABP grant limits which branch it may push. The fail tag's exact name is `gate/<agent>/<sha12>-fail`, where `<agent>` is the branch name after `work/` and `<sha12>` the first 12 hex characters of the refused head.

A section's dev-gate stays in `rulesets_held` (org/repos.json) until all three hold, and then one small IaC pull request moves it back: (a) its ABP grant allows pushing `work/<agent>` (cl-6.abp, P19); (b) cl-6.security has approved its new `scripts/release.sh`; (c) it reports one release that reached dev through `work/<agent>`. cl-6.security checks (b) and (c) when it reviews that pull request.

**What the gate judges (cl-6.security, 27 Nov 2026).** The App's gate judges the net file list of base...head on the protected paths only. A commit that touches a protected path and is later reverted therefore passes, because the net change is empty; only the tree is deployed, so that is accepted. Content and the signature of every commit, merges included, stay with each repository's own `check-signatures` on dev.

**Merges and the hold (cl-6.security, 27 Nov 2026).** Seven of the nine checks already verify signed merge commits (Data, Signals, Bulletins, Cyber, Events, Videos, Live). Library's refuses all merges and changes its own check, approved by cl-6.security, to accept a merge signed by an agent key from its first parent's `team/keys.json` with every commit it brings in checked. Travel has no signature check (S18). Library's and Travel's dev-gate stay held until each verifies every commit, merges included.

**Key pull requests land by fast-forward (cl-6.security, 27 Nov 2026).** Key bootstrap never calls the merge API: a rebase or merge commit would be GitHub's, not the agent's signed commits. It moves dev to the approved head with `PATCH refs/heads/dev`, force false, only when that head is a strict fast-forward of dev and every other condition holds; dev must then equal the approved head, or no anchor is set. A head that is not a fast-forward is refused: the agent merges `origin/dev` with a signed merge, pushes, and the new head is approved again.
